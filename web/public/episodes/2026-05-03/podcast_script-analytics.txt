Amir: Exactly. Without the need for *ingestion* or *ETL* for those ad-hoc queries or joining across systems. It extends the power of Unity Catalog – Databricks’ unified governance layer – to these external data sources. So, you can discover, manage, and govern these external assets right within Unity Catalog, and then query them using Databricks SQL or Spark with standard SQL syntax, as if they were native Delta tables.

Amir: Excellent questions, all highly relevant for a practitioner. Firstly, it’s largely complementary to tools like Fivetran. It’s not designed to replace full-scale, high-volume ETL for building your core data warehouse or data lake tables within Delta Lake. For that, you’ll still want robust ingestion and transformation pipelines. Think of it as a logical data integration layer rather than a physical one.

Dana: Okay, so it's not a full-blown data virtualization solution that replaces my entire data warehouse, but for analysts who need to join some historical data in Snowflake with some real-time data in Delta Lake without duplicating everything, this is a game-changer for speed and agility.

Amir: Precisely. And regarding performance, Databricks leverages "query pushdown" where possible. This means that instead of pulling all the data from the external source into Databricks to process, Databricks intelligently pushes parts of the query, like filters and aggregations, down to the source system. This maximizes efficiency and minimizes data transfer, so the performance is often quite good for the intended use cases.
